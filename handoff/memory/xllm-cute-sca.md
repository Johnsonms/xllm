Task (user, 2026-10-23 evening, after the step profile showed swift SCA at 58% of the 0.9B step): "去做 CuTe 的 sliding chunk attention kernel". File `xllm/modules/fused_ops/cute/sliding_chunk_attention.py`, wired as `sca_backend='cute'` in `xllm/modules/fused_ops/attention/sca.py` (falls back to swift with a warning for head dims > 256, prev chunk (CP), dropout), tests `tests/test_cute_sliding_chunk_attention.py` (13 cases). Branch cute-adaptive-working-memory (commits ab9065f + large-V commit, 2026-10-24).

**Design (V, S <= 256):** ScaFwd per (b, h, chunk, 128-row q tile): q tile resident in smem, 64-key K/V blocks in 2-stage TMA rings, S in TMEM (2 x 64 cols), P bf16 stored into TMEM as the A operand of the PV MMA (as in the official CuTeDSL fmha example at /data/home/johnson/cutlass/examples/python/CuTeDSL/cute/blackwell/kernel/attention/fmha/), O 256 cols; 4 softmax warps (thread = row), lazy O rescale (threshold 8 in log2 units). Mask = per-row key range [kmin(row), row] from `segment_starts`; blocks outside skipped. Saves y + lse2 (log2 domain, scale folded). Backward = 3 kernels: ScaBwdDv (per key tile, loops heads of the kv group x 64-query blocks up to `query_limits`), ScaBwdDk (V tile in TMEM as A of dP^T = V dO^T, Q block bytes reused as K-major and MN-major B - verified identical SW128 layouts), ScaBwdDq (mirror, dO in TMEM). A dS-materialized variant (write dS^T, cuBLAS dq) was slower (zero fill + transposed copies ~2.5 ms/layer) and used 4.3 GB - replaced by the fused dq kernel.

**Perf (B200, 1 GPU, cute AWM+TSDN in both):** 0.9B (B2 L16384) per layer fwd 0.83 ms / bwd 3.0 ms (swift ~12 / ~11); step 1151 -> 590 ms, peak mem 139 -> 40 GB. 4B (B1 L8192) step 967 -> 455 ms, 142 -> 37 GB (swift OOMs at L16384); the S=128 shape is MUFU (exp2) bound (FA4-style exp2 emulation on FMA units would help). 7.1B (V=2048, B1 L16384): fwd 0.77 / bwd 3.4 ms per layer via V slabs (ScaFwd/Dv recompute S per 256-wide slab) + dk/dq `load_dp` variants reading fp32 dP from cuBLAS (`torch.bmm(..., out_dtype=float32)` on chunk-major copies made by ChunkMajorCopy; torch permute copies ran at 1.7 TB/s); step 1050 -> 968 ms, 98 -> 81 GB. delta via RowDot kernel (fp32 casts cost 1 ms/layer on 7.1B). Remaining bwd cost 7.1B: dP GEMM 1.2 ms + dV 1.1 ms.

**Pitfalls learned:** (1) tcgen05.ld/st are warp-collective: a per-thread `if` around the O rescale hung intermittently -> `vote_any_sync` then all lanes execute with corr=1. (2) A finite mask stand-in (-1e30) scaled by scale2 < 1 passed the "-1e29" guard -> use -inf for masked scores (exp2 -> 0, fmax ignores). (3) Never commit a producer stage nobody consumes / call tail() on it (hang). (4) TVM-FFI fake tensors are int32-sized: >2^31 elements need a 2-D fake (`make_fake_compact_tensor(dtype, (sym, sym))`, pass a column-major view `.t()`); use Int64 offsets in-kernel. (5) Holding a pipeline stage across loop iterations: `consumer.clone()` gives a second state (waits ahead, releases behind) instead of carrying handles through dynamic loops. (6) TMEM pointer offsets (`tmem_ptr + cols`, `recast_ptr(..., BFloat16)`) work fine (the official example does it) - the earlier AWM note about stale data was a misdiagnosis.

# H200 (sm_90a, 141 GB HBM3e) report

See [README.md](README.md) for the branch contents, configuration fields and tests, and [H100.md](H100.md) for
the Hopper kernels: H200 is the same silicon, nothing was ported, every H100 item ran unchanged.

One pass, 2026-10-25/26, on 8 x H200 SXM 141 GB. Code: this branch's Hopper code; the pass added the DeepGEMM
backend of the fp8 GEMMs (`XLLM_FP8_DEEPGEMM=1`, `xllm/modules/fused_ops/fp8_sm90.py`), which replaced the H100
session's first integration. Harness: `docs/optimizations/harness/` (`fsdp_trace.py`; the `PIN_CPU`,
`FSDP_PREFETCH_DEPTH`, `EOS_RATE` knobs and the tokens / s line were added for this pass; `h200/summ.py`
summarises repeated runs, `h200/dg_bench.py`, `h200/nccl_bw.py`, `h200/bwd_09.py`, `h200/kcat.py` are the
microbenchmarks quoted below).

## TL;DR

- **The node is host-bound, not GPU-bound.** It is a KVM guest (cloud-hypervisor) on a Xeon Platinum 8470 whose
  effective clock switches between two speeds every few tens of seconds (single-thread Python loop 103-112 vs
  160-184 ms, ~1.55x; no steal time visible). The 0.9B / 4B steps were already near host-limited on H100 (4B:
  ~2.9 ms host per layer forward + 1.3 ms FSDP hooks vs ~3.8 ms GPU); here the CPU no longer runs ahead of the
  GPU, so FSDP2 issues each layer's all-gather late and the GPU waits (4B fp8 profiled step: 190 ms of
  compute-stream gaps in 560 ms vs 49-62 ms on H100). Step times are bimodal (the same config: 466 or 541 ms on
  0.9B; runs switch level mid-run). Everything below is >= 30 steps per run, 2-3 alternating repeats, medians of
  the pooled steady steps. **On a bare-metal H200 the host-bound rows would look different; re-check there
  before adopting the configuration changes.**
- The GPU itself is faster as expected: HBM copy 4.28 TB/s (H100 ~2.9, 1.47x); memory-bound kernels 1.26-1.44x
  per call; 1 GPU 0.9B B2 L16384 bf16 490 ms (H100 ~537-570).
- **What pays here: less host work per step.** FSDP layer groups (`fsdp_layers_per_group` 4 / 6 / 2) and
  `reshard_after_forward=False` (`FSDP_RESHARD=0`). With them: **0.9B 444 ms, 4B 419 ms, 7.1B 536 ms** (H100
  best 465 / 393-405 / 581-586; H200 with the H100 configs 467 / 453 / 576). Against the port baseline on this
  node: 2.42x / 1.82x / 2.02x.
- **7.1B at B1 L16384 fits without the FFN recompute** (118.8 GiB): 1048 ms, 15.4k tokens / s / GPU (with the
  recompute 1098 ms; H100: OOM without, ~1.70 s with).
- **DeepGEMM**, opt-in `XLLM_FP8_DEEPGEMM=1`: 1.10-1.35x per fp8 GEMM, bitwise equal to cuBLASLt on the same
  operands. End to end 7.1B -2 to -3% (150-step soaks: median 537 / 547 vs 554 / 555 ms); 0.9B and 4B within
  the node's noise (host-bound). Soaks track cuBLAS within 0.0015 through step 119; after that all four runs (2
  each) spike late (the random-token plateau nondeterminism seen on H100), DeepGEMM's higher in both pairs
  (10.71 / 10.56 vs 10.39 / 10.47). Not a default; decision below.
- Did not work: **swift SCA on 0.9B / 4B runs out of memory** even at 141 GB. **CUDA-graph blocks crash with
  EOS-packed data** (Xid 13 / illegal address): xattn's BOS plan and swift's host segment copy are computed on the
  host per step and get frozen into the graph. Without EOS the graph runs (4B fp8: 468-478 -> 431-454 ms, losses
  equal); with EOS it needs device-side / padded varlen metadata in xattn (decision below).

## How to run fastest on this H200 node

Build as on H100 (`python setup.py build_ext --inplace`, patched xattn from `docs/optimizations/patches/`);
DeepGEMM installed for the 7.1B row. All rows: `XLLM_FSDP_SYMM=1 NCCL_CTA_POLICY=2`, `fp8_gemm=True`, 8 GPUs,
per-rank batches, 30-step runs x 2.

## 0. Node and environment

- 8 x H200 SXM 141 GB (HGX: 700 W limit, SM 1980 MHz, HBM3e clock 3201 MHz), NV18 all-to-all, NVLS multicast
  available (not on the H100 node), driver 610.57.04 (CUDA 13.3). 156 vCPUs (KVM; GPUs 0-3 <-> CPUs 0-77, 4-7 <->
  78-155), 1.7 TB RAM.
- NCCL (2.30.7): 1 GB bf16 all-gather 321 GB/s bus bandwidth, 2 GB fp32 reduce-scatter 327 GB/s, same with
  `NCCL_NVLS_ENABLE=0` (`harness/h200/nccl_bw.py`).
- venv (uv, Python 3.12): torch 2.14.1+cu130, nvidia-cutlass-dsl 4.8.1, quack-kernels 0.6.5, triton 3.8.0, fla
  0.5.2 (`--no-deps`), pip CUDA 13.0 toolchain, `TORCH_CUDA_ARCH_LIST=9.0`.
- xattn v1.1.1 + `docs/optimizations/patches/xattn-1.1.1-local-full.patch`: `XATTN_TARGET_SM=90a MAX_JOBS=110 uv
  pip install --no-build-isolation -e .`, 640 units in 27 min. `xllm_extension` 7.7 min. Only one `uv pip install`
  into the venv at a time (uv locks it; a second one waits silently).
- DeepGEMM 2.8.2 (deepseek-ai/DeepGEMM 5081f85, 2026-10-20): needs GCC >= 13 (`<format>`); `gcc-13` from the
  ubuntu-toolchain-r PPA next to the default gcc 11, used only for it (`CC=gcc-13 CXX=g++-13 python setup.py
  bdist_wheel`, then `uv pip install dist/*.whl`). Kernels JIT-compile per shape on first use (step 0).
- ncu: `nsight-compute-2026.3.1` from the CUDA apt repo.
- torchrun: `--standalone` fails (the pod hostname does not resolve); `run1.sh` uses `--master_addr 127.0.0.1`.

## 4. DeepGEMM (plan §7: decision A by the owner, 2026-10-25)

- Microbenchmark (`harness/h200/dg_bench.py`): 30 GEMMs (fwd / dgrad / wgrad of 10 gekko linears) 13.87 -> 11.77
  ms; per GEMM 1.10-1.35x, one slower (4B q wgrad 131 -> 148 us). Bitwise equal to cuBLASLt on the same operands.
  Constraints: sm90 DeepGEMM takes only A 1 x 128 / B 128 x 128 (so the weight gradient tiles X^T:
  `XLLM_FP8_SM90_WGRAD_TILE=x`, the default under DeepGEMM; a numerics change vs the dY^T tiling), and no C /
  residual with bf16 output (the residual GEMMs keep the cuBLASLt epilogue op).
- Integration: `fp8_sm90.mm` behind `XLLM_FP8_DEEPGEMM=1`, cuBLASLt default and fallback; `test_mm_deepgemm`.
  `XLLM_FP8_DEEPGEMM_SMS` caps the SMs of its persistent kernels (124 / 116: no effect on 7.1B, 540-542 vs 554
  cuBLAS, or 0.9B; H100 had measured 120 as best next to the overlapped reduce-scatter). Default: all SMs.
- End to end: helps 7.1B only (above). 0.9B across four batches 457 / 490 / 432 / 495 ms vs 442-444 without:
  within this node's noise, not a systematic loss; not host cost (host per GEMM call: DeepGEMM 21-28 us vs
  `_scaled_mm` 24-26 us) and not the X^T weight-gradient tiling (`WGRAD_TILE=x` alone 448 vs 443).

## 5. Host cost per launch (this node, one GPU, small shapes)

torch elementwise op 4.8 us, `torch.empty` 1.8 us, `_scaled_mm` 24 us, CuTe DSL kernel (tvm-ffi) 19.5 us, Triton
`_fp8_kernel` 22-26 us through the JIT (14.0 us calling the compiled kernel's `run` directly, same output),
`fp8_sm90._empty` 8 us per operand. A 4B fp8 step launches ~6500 kernels, ~940 of them Triton: a direct Triton
launcher would save ~7.5 ms / step (~2%, below the noise here; H100 measured the same idea at 414 -> 413.5 ms), not
done. py-spy of rank 0 (8 GPUs, 4B): no single hotspot; the host time is spread over the launches (`_scaled_mm`
5.6% self the largest).

CUDA graphs with EOS: the data-dependent host state inside the block is xattn's BOS plan (`_build_bos_plan`:
`int(max_seqlen)`, `int(num_runs)` set the varlen grid, a host sync per call) and, for 7.1B, swift's host copy of
the segment ids (`sca.py` `_swift_seg_cache`). TSDN's tile count is shape-only; the conv / AWM segment caches are
device tensors. Making the graph path work means a fixed-capacity varlen plan in xattn (max_seqlen = L, padded
cu_seqlens, empty runs exit early) and a device-side or fixed-split swift layout.

Of the H200 plan written after the H100 work: §1 environment / baselines, §2 carry-over, §3.1-3.5 (no
recompute, 7.1B L16384, swift on 0.9B / 4B, CUDA graphs, less sharding), §4.1 (DeepGEMM; fp8 default left to the

not, for the reasons above. §5 (no-gain items from H100) was not repeated.

## 7. Decisions for the owner

1. **DeepGEMM as a default for 7.1B?** -2 to -3% on this node, soaks equal through 120 steps, late spikes higher
   in both DeepGEMM soaks (2 runs each; the harness's random-token plateau makes late steps noisy). Suggest a
   real-data loss comparison first; keep opt-in until then.
2. **fp8 / symm reduce-scatter as defaults** (open from H100): fp8 is in every best row here too.
3. **`fsdp_layers_per_group` > 1 for 0.9B / 4B** (holds more unsharded layers at once: memory ok on 141 GB) -
   worth it wherever the host is the limit; re-measure on bare metal.
4. **CUDA graphs with EOS-packed batches** need xattn (and swift) to take padded / device-side varlen metadata
   (fixed-capacity cu_seqlens, max_seqlen = L, empty segments) so the grid does not depend on the batch: an xattn
   change worth ~6% on 4B here (no-EOS measurement). Upstream to xattn or not.
5. **Training recipe**: 7.1B at L16384 without FFN recompute now fits; larger per-rank batches would cut host
   cost per token on this node.
6. xattn patches upstream (open from H100).
